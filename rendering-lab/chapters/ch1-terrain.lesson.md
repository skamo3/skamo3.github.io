# Ch1 · 지형 — 정점 변위(vertex displacement)

> Ch1 누적 월드의 첫 겹. 평평한 판의 각 정점을 정점 셰이더에서 위로 밀어 언덕진 지형을 만든다. Ch0의 uWobble(정점 흔들기)을 목적을 가진 형태로 확장하는 단계다.

## 이 개념에서 배우는 것

- 정점 셰이더에서 정점 위치를 바꿔 형태 자체를 만들어내는 방법(vertex displacement)
- 높이맵의 본질 — "위치 → 높이"로 가는 함수/룩업
- 왜 이 작업이 CPU가 아니라 GPU(정점 셰이더)에서 일어나는가
- 정점을 옮기면 법선이 어긋난다는 문제(→ Ch2 조명의 복선)

## 이론

지형은 결국 **평면 위 각 점의 높이**다. 평평한 판(수천 개의 정점)을 준비하고, 각 정점의 높이를 그 정점의 (x, z) 위치로 결정하면 언덕이 생긴다.

```
height = f(x, z)
정점.y += height
```

여기서 `f`가 **높이맵**이다. 실제 엔진에서는 회색조 텍스처를 샘플링해 높이를 읽지만(밝을수록 높음), 이 데모에서는 텍스처 없이 **절차적 노이즈(fbm)** 함수로 높이를 만든다. "위치를 넣으면 높이가 나온다"는 본질은 같다.

정점마다 이 계산을 해야 하는데, 정점이 수천~수만 개라 **정점 셰이더에서 GPU가 병렬로** 처리한다. CPU에서 매 프레임 정점을 옮기면 draw call 준비 비용(Ch0에서 본 그 병목)이 폭발한다.

## 이론 → 코드 매핑

`worlds/ch1-terrain.js`에서

- `PlaneGeometry(20, 20, 120, 120)` = 120×120으로 잘게 쪼갠 판. 정점이 촘촘해야 부드러운 지형이 나온다
- vertex shader의 `fbm(pos.xy * uFreq)` = 이 정점 위치의 높이 `f(x, z)`
- `uAmp`(높이 배율), `uFreq`(굴곡 빈도) = 지형을 조절하는 uniform(파라미터)
- `vH` varying = 계산한 높이를 프래그먼트로 넘겨 높이별 색(풀→흙→봉우리)에 사용
- 판은 로컬 XY 평면이라, 위로 미는 축은 로컬 +Z다 (`pos.z` 를 올린다)

## 실습 (직접 채우기)

vertex shader의 TODO 한 줄 — 계산된 높이 `h`만큼 정점을 위로(로컬 +Z) 민다.

```glsl
// 현재 (변위 없음 — 높이 색만 입혀진 평평한 판)
// pos 그대로

// 목표 (정점을 높이만큼 밀어 3D 지형으로)
pos.z += h * uAmp;
```

## 관찰 포인트 (채우기 전 / 후)

- **전**: 판이 평평한데 높이 패턴에 따라 색만 칠해져 있다(위에서 본 지도처럼)
- **후**: 색 패턴 그대로 정점이 솟아올라 입체 지형이 된다
- **와이어프레임**을 켜면 격자 자체가 솟는 게 보인다 — 정점이 움직였다는 직접 증거
- `uAmp`(높이), `uFreq`(굴곡 수) 슬라이더로 지형을 바꿔본다

## 왜 정점 셰이더인가 (Ch0과의 연결)

Ch0의 uWobble도 정점을 밀었지만 장식이었다. 여기서는 **형태 자체를 정점 변위로 만든다**. 같은 원리(GPU가 정점을 병렬로 옮김)를 목적을 가지고 쓰는 것이다. 지형·물결·바람에 흔들리는 풀이 전부 이 한 가지 아이디어의 변주다.

## 다음으로 이어지는 문제 (법선)

정점을 옮기면 **법선(normal)은 원래 평면 기준 그대로**라, 빛을 비추면 음영이 엉뚱하게 나온다. 그래서 지금은 조명 없이 높이별 색만 입혔다. 정점을 바꾼 뒤 법선을 다시 계산하는 문제는 **Ch2(빛과 재질)**에서 다룬다.

## 엔진 매핑

- **UE**: Landscape(하이트맵 기반 지형), Material의 **World Position Offset**으로 정점 변위, 하이트맵 텍스처 샘플링
- **Unity**: Terrain 컴포넌트(heightmap + splatmap 레이어), 셰이더 `vert` 함수에서 정점 변위, `tex2Dlod`로 정점 단계 텍스처 샘플
- **D3D**: vertex shader에서 `SV_Position` 출력, displacement mapping, vertex texture fetch(정점 단계 텍스처 읽기)

## 개념2 · Mesh 인스턴싱을 이용한 풀 표현

핵심 기법은 **Mesh Instancing** — 같은 메시를 대량으로 한 번에 그리는 것이고, 풀은 그 응용 예다(나무·바위·군중도 같은 기법). 지형 위에 풀 수천 포기를 올리며, Ch0에서 본 **draw call 병목의 정면 해법**을 쓴다.

### 이론

풀 한 포기씩 따로 그리면 draw call이 포기 수만큼 생겨 CPU가 못 버틴다. 인스턴싱은 **지오메트리 하나 + 셰이더 하나 + 인스턴스별 변환 배열**을 GPU에 한 번에 넘겨, 한 번의 draw call로 수천 개를 그린다.

- `InstancedMesh(geometry, material, count)` = 인스턴싱 묶음
- 각 인스턴스의 변환(위치·회전·크기)은 4×4 행렬 하나 → `setMatrixAt(i, matrix)`로 등록
- 정점 셰이더가 `instanceMatrix`를 자동으로 곱해 각 인스턴스를 제 위치에 그린다

### 지형 표면에 앉히기

풀은 지형 높이 위에 있어야 한다. 지형 높이는 GPU 셰이더의 fbm이 만드니, CPU에서도 **같은 fbm**(`jFbm`)을 계산해 위치를 정한다. 판이 -90°X 회전이라, 로컬 (lx, ly) 지점의 표면 월드좌표는 `(lx, height, -ly)`, `height = uAmp * fbm(...)`.

### 실습 (직접 채우기)

`scatter()` 안 TODO — 각 인스턴스의 변환을 만들어 등록한다.

```js
// 정답
dummy.position.set(lx, height, -ly);
dummy.rotation.y = Math.random() * Math.PI * 2;
dummy.scale.setScalar(0.6 + Math.random() * 0.7);
dummy.updateMatrix();
grass.setMatrixAt(i, dummy.matrix);
```

### 관찰 포인트

- **전**: 인스턴스 행렬이 0이라 풀이 아예 안 보인다(지형만)
- **후**: 풀 4,000포기가 지형 표면에 흩뿌려진다 — 전부 draw call 한 번
- `높이`/`굴곡` 슬라이더를 바꾸면 풀이 새 지형 표면에 다시 앉는다

### 왜 Ch0과 이어지나

Ch0에서 "draw call 많으면 CPU 병목"을 배웠다. 인스턴싱은 4,000번을 1번으로 줄이는 그 해법이다. 풀·나무·바위처럼 같은 것이 대량으로 필요한 곳의 표준 기법.

### 엔진 매핑

- **UE**: Instanced Static Mesh(ISM) / Hierarchical ISM(HISM), Foliage 도구
- **Unity**: `Graphics.RenderMeshInstanced` / BatchRendererGroup, GPU Instancing
- **D3D**: `DrawIndexedInstanced`, 인스턴스 버퍼
