## 1. 논문이 푼 문제

부서지는 파도는 단면이 말려 들어가는(overhang) 모양이라 높이맵(heightfield)으로 표현이 안 된다. 높이맵은 (x, z)마다 높이가 하나뿐인데, 말린 파도는 같은 (x, z) 위에 수면이 2~3겹 겹친다. 그렇다고 유체 시뮬레이션을 실시간으로 돌리는 건 PS4/PS5에서도 불가능하다.

Guerrilla의 선택은 하이브리드다.

- 오프라인(Houdini)에서 작은 영역의 파도를 시뮬레이션하고 결과를 텍스처로 굽는다
- 런타임에는 그 데이터를 인스턴싱해서 재생·블렌딩하고, 해안선 모양에 맞게 휘어 붙인다
- 시뮬레이션의 사실적인 3D 움직임은 가져오고, 모양은 아트가 원하는 대로 구부린다

이전 사례(Killzone 3의 스트리밍 메시, CoD WWII의 루프 Houdini 시뮬)는 "통째로 구워서 재생"이었다. 길고 복잡한 해안선에는 그게 안 맞아서, 재사용 가능한 작은 단위로 쪼갠 게 이 발표의 핵심 기여다.

## 2. 핵심 근사: 파도 = 단면 하나가 파면을 따라 이동

말려서 부서지는 파도를 보면, 일정한 단면(cross section)이 파면(wavefront) 방향으로 평행이동하는 것처럼 보인다. 그래서 **애니메이션되는 2D 단면 하나**만 있으면, 파면 위 어느 지점 어느 시각의 모양이든 그 단면의 특정 프레임으로 설명할 수 있다.

### 2-1. 단면 변형 텍스처 (Deformation texture)

| 축 | 의미 |
|---|---|
| U (가로) | 파도를 앞뒤로 가로지르는 위치 (back-to-front) |
| V (세로) | 애니메이션 파라미터. 0 = 평평 → 0.27 솟기 시작 → 0.4 가팔라짐 → 0.5 말려서 거품 → 끝 = 다시 평평 |
| RGB | 평평한 수면 위 점을 어디로 옮길지(XYZ 오프셋) |

- 한 프레임의 단면 = 텍스처의 가로 한 줄. 모든 프레임을 세로로 쌓아 2D 텍스처 한 장이 된다
- 오프셋은 "평평한 면에서 얼마나 밀어내나"로 저장한다. 그래서 강도를 0으로 줄이면 원래 평면으로 자연스럽게 돌아간다
- 애니메이션은 반드시 평평한 상태로 끝나야 한다. 그래야 변형을 끝낼 때 튀지 않는다
- 말린 파도 안쪽 고리(inner loop)도 단면에 포함해야 한다. 파도 터널 안을 들여다볼 수 있기 때문이다. 대가로 단면 곡선 길이가 크게 늘고 삼각형이 늘어난다
- 실제 제작에서도 Houdini 추출본은 손볼 게 너무 많아서 결국 **손으로 애니메이션한 곡선**을 썼다. 이 Lab에서 절차적으로 단면 곡선을 만드는 것도 논문과 같은 길이다

### 2-2. 부가 텍스처

위치만으로는 셰이딩이 안 된다.

- **편미분 텍스처**: 위치 오프셋을 U·V로 미분한 값을 미리 구워둔다. 탄젠트/바이노멀(→ 노멀맵)을 여기서 바로 만든다. 이웃 정점을 다시 읽어 차분하지 않아도 된다
- **UV 보정 텍스처**: 변형이 날카로운 모서리 쪽으로 정점을 몰아넣기 때문에, 수면 텍스처 UV가 뭉개지지 않게 보정값을 같이 굽는다
- **정점 컬러**: 거품 생성 위치, 상대 높이, 변형 강도를 프래그먼트 셰이더로 넘긴다

HFW 전체에서 부서지는 파도 변형은 이 텍스처 세트 **하나**만 썼다.

## 3. 파면의 모양과 움직임

### 3-1. (시간, 횡거리) → 월드 위치

파면은 2D 정의역 위의 함수로 정의된다.

- 가로축 `s` = 파면을 따라 잰 거리(transverse distance)
- 세로축 `t` = 시간
- `t` 고정, `s` 변화 → 그 순간의 파면 모양
- `s` 고정, `t` 변화 → 한 점이 해안으로 밀려가는 경로(path)

아티스트 도구의 곡선 두 종류가 이 정의역의 축 정렬 선에 대응한다.

| 곡선 | 정의역에서 | 역할 |
|---|---|---|
| Shape curve (빨강) | `t` = 상수인 선 | 특정 시각의 파면 모양 |
| Guide curve (노랑) | `s` = 상수인 선 | 파면의 양 끝, shape curve 사이 연결 정보 |

임의의 (s, t)는 자신을 감싸는 shape 2개 + guide 2개 사이에서 **Coons patch**로 보간한다 (Coons, 1967).

```
c0(s), c1(s)  : 아래/위 shape curve      d0(t), d1(t) : 왼/오 guide curve

Lc(s,t) = (1-t)·c0(s) + t·c1(s)                     // shape 사이 선형 보간
Ld(s,t) = (1-s)·d0(t) + s·d1(t)                     // guide 사이 선형 보간
B(s,t)  = c0(0)(1-s)(1-t) + c0(1)s(1-t)
        + c1(0)(1-s)t     + c1(1)st                 // 네 모서리 쌍선형
P(s,t)  = Lc + Ld - B
```

`Lc`와 `Ld`를 더하면 모서리 기여가 두 번 들어가서 `B`를 한 번 뺀다. 결과는 네 경계 곡선과 정확히 일치한다.

### 3-2. 어디서 부서지나: animation curve

파면 모양만으로는 "어디서 부서질지"를 못 정한다. 그래서 월드에 animation curve를 그어 그 위치의 애니메이션 파라미터(V)를 지정한다. 경로(path)를 따라가며 animation curve와의 교점을 찾고, 교점 값 사이를 블렌딩한다. 그래서 디버그 화면이 파면이 아니라 파면에 수직인 경로로 그려진다.

### 3-3. 굽기 (가장 중요한 최적화)

Coons 보간 + 경로 추적은 런타임에 매번 계산하기엔 비싸다. 그래서 (t, s) 격자에서 **월드 위치 + 애니메이션 파라미터**를 미리 샘플링해 저장하고, 런타임은 그 표를 읽기만 한다. 이 Lab에서 "실시간 계산 vs 베이크"를 직접 비교하는 첫 실험이 여기다.

### 3-4. 여러 파도와 변주

- 동시에 활성화된 파면 여러 개가 **같은 애니메이션 데이터를 서로 다른 시간으로** 샘플링한다 → 연속으로 밀려오는 파도
- 전부 똑같아 보이는 걸 막으려고 **변주 텍스처**를 쓴다. 한 줄 = 파면 하나, 값 = 변형 강도. 검정이면 그 구간은 안 부서진다(gap)
- gap을 애니메이션 파라미터로 만들면 안 된다. 파라미터 0인 구간과 1인 구간 사이에 중간 모양이 전부 늘어서기 때문이다. 그래서 강도라는 별도 축이 필요하다

## 4. 런타임: 쿼드로 만든다

1. 파면 모양을 앞뒤로 늘려 **쿼드 줄**을 만든다. 쿼드 하나 = 네 꼭짓점 위치 + 왼쪽/오른쪽 애니메이션 파라미터
2. 컴퓨트 셰이더가 수면의 정점마다 자신을 포함하는 쿼드를 찾는다
3. 쿼드 안 상대 좌표를 구한다. 앞뒤 방향 = 변형 텍스처의 U, 좌우 방향으로 양쪽 애니메이션 파라미터를 보간한 값 = V
4. 변형 텍스처를 샘플링 → 오프셋을 쿼드 방향에 맞게 회전 → 여러 쿼드의 변위를 블렌딩
5. 최종 위치·탄젠트·정점 컬러를 정점 버퍼에 써넣는다

변형이 수면을 2~3배 이상 늘리기 때문에 파면 근처는 아주 촘촘하게 테셀레이션해야 한다. 발표 끝의 "Future work"도 결국 삼각형 부족 문제였다. 출시 직전에 파도 주변만 테셀레이션을 올리고 나머지를 살짝 낮춰 균형을 맞췄다.

# 설계

## 6. 렌더러: WebGPU 컴퓨트

논문 구조(컴퓨트가 정점 버퍼 생성 → 렌더 패스가 그대로 사용)를 그대로 따라가려고 WebGPU를 쓴다.

- `three/webgpu`의 `WebGPURenderer` + TSL(`three/tsl`)의 `Fn().compute(count)`, `instancedArray`/`storage` 버퍼
- 주의: `three/webgpu` 빌드는 코어를 자체 포함한다. 이 월드 안에서는 `three`와 섞지 말고 전부 `three/webgpu`에서 가져온다
- 필터링되는 텍스처 포맷은 `rgba16float`로 한다. `rgba32float` 선형 필터링은 `float32-filterable` 기능이 있어야 한다
- GPU 시간 측정: `new WebGPURenderer({ trackTimestamp: true })` + `renderer.resolveTimestampsAsync(...)` 후 `renderer.info.compute/render.timestamp`. 브라우저가 `timestamp-query`를 지원해야 하고, three.js 버전마다 API가 조금씩 달라서 구현할 때 사용 버전 기준으로 확인한다
- importmap: 기존 월드는 three@0.169 그대로 두고, `"three/webgpu"`, `"three/tsl"`만 three@0.184.0으로 매핑했다 (P1에서 결정). webgpu 빌드는 코어를 자체 포함해서 두 버전이 한 페이지에 공존할 수 있고, 기존 월드 회귀 위험이 없다. 대가로 이 월드에 처음 들어갈 때 코어를 한 벌 더 받고, 콘솔에 "Multiple instances of Three.js" 경고가 뜬다. 같은 이유로 `three/addons`(0.169 코어에 묶임)는 이 월드에서 쓰지 않는다. 궤도 카메라도 직접 만들었다

### 하네스 확장

캔버스 하나는 한 번 `webgl2` 컨텍스트를 잡으면 `webgpu`로 바꿀 수 없다. 그래서:

- 레지스트리에 새 챕터 `Ocean Wave` 항목(id `ocean-wave`, 파일 `worlds/ocean-wave.js`)을 두고 `renderer: 'webgpu'` 필드 추가 (없으면 기존 WebGL)
- 하네스가 렌더러 종류가 바뀔 때 `<canvas>`를 새로 만들어 교체하고, 이전 렌더러는 `dispose()`
- WebGPU는 `await renderer.init()` 후 `renderer.setAnimationLoop` 또는 `renderAsync`로 그린다
- 월드 계약(`create → { scene, camera, update, dispose }`)은 그대로 두고, `update(dt)` 안에서 `renderer.compute(...)`를 호출하게 한다

## 7. 씬 구성

- **해변**: 만(bay) 모양으로 휘어진 해안선 높이맵. 바다 쪽으로 완만하게 깊어진다. 해안선 곡선은 shape curve의 마지막 줄과 공유한다
- **수면**: 해변을 덮는 평면 격자. 정점 위치는 컴퓨트가 매 프레임 써넣는다
- **하늘/태양**: 단색 그라디언트 + 방향광. 반사는 하늘색 근사(Fresnel)만. 본격 반사·굴절은 Ch4에서
- **카메라**: 기본은 3인칭 캐릭터 카메라(14장). 디버그용 자유 카메라(OrbitControls)로 토글 가능. 시작 위치는 해안 근처 저각도 (말린 파도 안쪽이 보이는 각도)

## 8. 데이터 (init에서 CPU로 생성 = "오프라인 베이크" 역할)

| 이름 | 크기 예시 | 내용 |
|---|---|---|
| `deformTex` | U 128 × V 64, rgba16float | 단면 오프셋 (rg = 진행 방향/위, b = 거품량) |
| `derivTex` | 같은 크기 | ∂offset/∂u (탄젠트 계산용) |
| `waveLUT` | t 64 × s 32, rgba16float | 파면 격자 월드 위치 xz + 애니메이션 파라미터 + (예비) |
| `variationTex` | s 64 × 파면 수 | 파면별 변형 강도 (gap) |

단면 곡선 생성 규칙 (V 구간별):

- 0 ~ 0.3: 가우시안 융기, 높이 증가
- 0.3 ~ 0.5: 앞면이 가팔라지고 마루가 앞으로 쏠림
- 0.5 ~ 0.65: 마루 끝(lip)이 앞면보다 앞으로 나가 아래로 떨어짐 → overhang + inner loop
- 0.65 ~ 1: 진폭이 0으로 줄며 거품량만 남음 → 평평하게 끝남

## 9. 프레임당 GPU 파이프라인

```
[CPU] 활성 파면 K개의 시간 t_k 갱신 (uniform)
  │
  ▼
[compute A] 파면 쿼드 생성        스레드 = K × S
  waveLUT(t_k, s_j) 샘플 → 파면 앞뒤로 늘려 쿼드 4꼭짓점
  + 좌/우 애니메이션 파라미터 + 강도(variationTex) → quadBuffer
  │
  ▼
[compute B] (실험 E2-on) 쿼드 타일 비닝   스레드 = 쿼드 수
  쿼드 AABB가 겹치는 화면/월드 타일 리스트에 atomic append
  │
  ▼
[compute S] 로컬 다이나믹 웨이브 시뮬 (13장)   스레드 = 시뮬 셀 수, 서브스텝 N회
  창 이동(토로이달 스크롤) → 플레이어 입력 주입 → 파동 방정식/SWE 한 스텝
  → 가장자리 흡수층 감쇠 → simTex (높이 η, 속도)
  │
  ▼
[compute C] 수면 변형              스레드 = 정점 수
  내 정점이 들어간 쿼드 찾기 → 쿼드 내 (u, v) → deformTex 샘플
  → 쿼드 방향으로 회전 → 블렌딩 → (베이크 변위)
  + 창 안이면 simTex 샘플 → 높이 η 가산, 기울기로 노멀 보정 (13-4)
  → positionBuffer / normalBuffer / foamBuffer
  │
  ▼
[render] 수면 메시: positionBuffer를 정점 위치로 바로 사용
  프래그먼트: 수심 색 + Fresnel 하늘 반사 + 태양 하이라이트 + 거품
```

쿼드 안 상대 좌표는 쿼드를 두 삼각형으로 나눠 무게중심 좌표로 구하거나, 쌍선형 역변환(뉴턴 2~3회)으로 구한다. 앞쪽이 싸고 뒤쪽이 매끄럽다. 이것도 비교 대상이다.

### P2 구현 메모

- 단면 곡선은 `worlds/ocean-wave-section.js`. "호 길이에 따른 접선 각도 φ(s)"로 정의하고 적분해서 만든다. 각도로 정의하면 고리가 생겨도 곡선이 매끄럽고, 무너질 때 모든 각도에 0으로 가는 배율을 곱하면 고리가 풀리며 평평해진다. three 의존성이 없어서 Node로 모양을 따로 검증할 수 있다

- 수면 격자는 x 0.5 m, z는 먼바다 1 m / 파도가 말리는 구간(z > -75) 0.125 m. 약 60만 정점, 120만 삼각형. 직선 파면이라 z만 나눴고, 곡선 파면(P3)에서는 E3처럼 파면 근처만 촘촘하게 하는 방식이 필요하다
- 쿼드는 아직 CPU에서 만들어 storage 버퍼로 올린다(쿼드 52개). P3에서 waveLUT를 읽는 compute A로 옮긴다
- V는 쿼드 경계마다 따로 둔다. H/d로 0~0.5까지 올리고, 0.5(말리기 시작)부터는 수심과 상관없이 시간으로 진행(약 4초)
- 관찰 키: Space 일시정지, 1/2/3 재생 속도, F 파도 따라가기, C 시점 전환. `?debug`를 붙이면 P 키로 GPU 정점 버퍼를 읽어 x = 0 단면을 `<pre id="ocean-debug">`에 JSON으로 남긴다 (GPU 결과가 CPU 곡선과 같은지 확인용)

# 확장: 플레이어 주변만 실시간 시뮬레이션

## 13. 다이나믹 웨이브

### 13-1. 왜 "다 굽고 주변만 시뮬"인가

| | 베이크 (논문) | 실시간 시뮬 |
|---|---|---|
| 비용 | 넓이와 거의 무관 (텍스처 읽기) | 셀 수 × 서브스텝 수에 비례 |
| 반응 | 없음. 캐릭터가 지나가도 물이 모름 | 발자국 물결, 항적, 다리에 부딪혀 갈라지는 파도 |
| 사실성 | 아트가 다듬은 큰 파도 | 작은 파동은 사실적, 큰 부서지는 파도는 못 만듦 |

둘의 장점이 겹치지 않는다. 큰 파도는 베이크가, 플레이어 눈앞 수십 m의 작은 상호작용은 시뮬이 맡는다. 플레이어가 디테일을 알아볼 수 있는 거리가 한정돼 있으니 시뮬 비용도 그 범위로 묶인다.

시작값: 창 32 m × 32 m, 셀 0.25 m → 128 × 128 셀. E8에서 크기·해상도를 바꿔 잰다.

### 13-2. 시뮬 모델 두 가지 (E7에서 비교)

**A. 선형 파동 방정식 (수심 반영)**

```
∂²η/∂t² = c²·∇²η − k·∂η/∂t        c = √(g·d),  d = 그 셀의 수심
이산화(Verlet):  η⁺ = η + (1−k·dt)(η − η⁻) + (c·dt/dx)²·(η_L + η_R + η_T + η_B − 4η)
```

- 상태: `η`(현재), `η⁻`(이전) 두 장. 핑퐁
- `c = √(g·d)`라서 얕은 곳으로 갈수록 파동이 느려진다. 그러면 파면이 해안선과 평행하게 꺾이는 굴절이 따로 코드 없이 생긴다
- 지형이 수면보다 높은 셀은 벽(η = 0 고정)이라 해변에서 반사파가 생긴다
- 안정 조건(CFL): `c·dt/dx ≤ 1/√2`. 수심 1.5 m(c ≈ 3.8 m/s), dx 0.25 m면 dt ≤ 0.046 s → 60 fps에서 1스텝. 수심 5 m면 2스텝. 창 안 최대 수심으로 서브스텝 수를 정한다
- 한계: 물이 모래 위로 올라오지 못한다(run-up 없음). 물이 "있는 곳"이 고정이다
- **주의 (분산)**: 발로 만든 물결은 파장 0.3~1 m라 수심 1 m에서도 깊은 물 영역(d > λ/2)이다. 실제 속도는 √(gλ/2π) ≈ 0.7~1.25 m/s인데 √(g·d)를 쓰면 3.1 m/s로 2.5~4배 빠르다. 그래서 플레이어 물결용 시뮬은 c에 상한(예: 1.5 m/s)을 두거나 iWave(Tessendorf 2004)처럼 분산을 넣는다. √(g·d)는 해변을 타고 오르는 긴 물(SWE)에만 쓴다. c 상한을 낮추면 CFL이 느슨해져 서브스텝도 준다

**B. 얕은 물 방정식 (SWE, virtual pipe 모델)**

- 상태: 셀마다 물 깊이 `h` + 이웃 4방향으로 나가는 유량 `f(L, R, T, B)`
- 스텝: 수면 높이(지형 + h) 차이로 유량 가속 → 셀에서 나가는 총량이 가진 물보다 많으면 비율로 줄임(음수 깊이 방지) → 들어온 양 − 나간 양으로 `h` 갱신
- `h = 0`인 마른 셀이 자연스럽게 다뤄져서 물이 해변을 타고 올라왔다(swash) 빠지는 게 나온다
- 비용은 A보다 2~3배. 셀당 버퍼도 더 크다

계획: P6은 A로 시작해 파이프라인(이동 창·입력·합성)을 먼저 완성하고, P7에서 같은 인터페이스로 B를 끼운다.

### 13-3. 플레이어를 따라 움직이는 창

- 창 중심 = 플레이어 위치를 셀 크기로 스냅한 값. 스냅 안 하면 매 프레임 재샘플링이 생겨 파동이 번진다
- **토로이달 주소**: 텍스처 좌표 = `월드 셀 좌표 mod N`. 창이 k셀 움직이면 텍스처 전체를 복사하지 않고, 새로 들어온 k줄만 초기화한다 (A: η = 0, B: h = 베이크 수면 − 지형)
- **흡수층(sponge)**: 가장자리 8셀 정도에서 감쇠를 0 → 강하게 올린다. 없으면 창 경계에서 파동이 반사돼 되돌아온다
- 합성할 때도 가장자리로 갈수록 가중치를 0으로 내려서 창 경계가 수면에 선으로 보이지 않게 한다

### 13-4. 베이크 파도와 결합

1. **기본은 덧셈**: 최종 위치 = 베이크 변위 + 창 가중치 × η(수직). 노멀은 η의 중심 차분 기울기로 베이크 노멀을 기울인다
2. **말린 부분 보호**: 부서지는 순간(애니메이션 파라미터 0.4~0.65, 강도 큼)에는 η를 줄인다. 수직 오프셋을 overhang 위에 그대로 더하면 lip이 찢어진다
3. **에너지 넘겨주기**: 논문의 단면 애니메이션은 부서진 뒤 평평하게 끝난다. 그 순간 베이크가 들고 있던 물을 시뮬에 소스로 넣는다 (파면을 따라 띠 모양 높이/부피 펄스). 그러면 부서진 파도의 잔여 물(bore)이 시뮬 안에서 해변을 타고 올라간다. "부서지기까지는 베이크, 그 뒤 해변을 적시는 건 시뮬"로 역할이 나뉜다. B 모델에서 효과가 제대로 보인다
4. **메시 해상도**: 수면 정점 간격이 시뮬 셀보다 넓으면 시뮬 디테일이 사라진다. 플레이어 주변은 메시도 셀 크기 이하로 촘촘해야 하고, 그래서 E3(파도 근처 고밀도)의 LOD 중심에 플레이어 위치도 들어간다. 메시보다 작은 물결은 프래그먼트 셰이더에서 η 기울기를 노멀로만 쓰는 방법도 같이 비교한다

### 13-5. 캐릭터 → 물 입력

캐릭터를 구 몇 개(두 다리 + 몸통)로 근사한다.

- **장애물**: 구가 물에 잠긴 셀은 η를 고정(A) 또는 벽(B)으로 처리 → 다리에 부딪힌 파동이 갈라지고 뒤쪽에 그늘이 생긴다
- **부피 소스**: 이번 스텝과 지난 스텝의 "잠긴 부피" 차이를 그 셀의 수면 변화로 넣는다. 움직이면 앞은 솟고 뒤는 꺼져서 항적이 생기고, 가만히 서 있으면 차이가 0이라 조용해진다
- **발 디딤**: 발이 물에 닿는 순간 짧은 임펄스 → 발자국 물결

### 13-6. CPU가 물 높이를 알아야 할 때

캐릭터 이동(물 깊이에 따른 속도), 카메라가 물속으로 들어가는지 판정에 수면 높이가 필요하다.

- 베이크 부분은 CPU에도 같은 데이터(`waveLUT`, 단면 곡선)가 있으니 CPU에서 똑같이 계산한다
- 시뮬 부분은 플레이어 주변 4 × 4 셀만 작은 버퍼에 복사해 **비동기 읽기**(`getArrayBufferAsync`)한다. 1~2프레임 늦은 값이지만 걷는 속도 조절엔 충분하다
- 동기 읽기(GPU 끝날 때까지 기다리기)는 파이프라인을 멈추게 하니 쓰지 않는다

## 14. 3인칭 캐릭터

### 14-1. 이동

- WASD = 카메라 기준 방향 (카메라 yaw를 수평면에 투영한 앞/옆). Shift 달리기
- 가속·감속 보간, 캐릭터는 이동 방향으로 부드럽게 회전
- 지면: 지형이 해석적 높이 함수라 물리 엔진 없이 `y = terrainHeight(x, z)`. 경사 한계 넘으면 못 올라감
- 물 깊이 `d = 수면 높이 − 지형`에 따라 속도 배율: 발목(0.2 m) 0.9, 무릎(0.5 m) 0.6, 허리(1.0 m) 0.35
- **d > 1.2 m면 진입 거부**. 해안 + 얕은 해변만 돌아다니게 하는 경계가 이것 하나로 된다. 파도가 밀려와 순간 깊어지는 건 거부가 아니라 뒤로 살짝 밀리는 힘으로 처리

### 14-2. 카메라

- 마우스 yaw/pitch, Pointer Lock API (캔버스 클릭으로 잠금, Esc로 해제 → 사이드바 사용 가능). pitch 제한
- 어깨 뒤 스프링 암, 따라가기는 임계 감쇠 스프링으로 부드럽게
- 카메라가 지형 아래로 들어가면 들어올림. 수면 아래로 내려가면 수면 위로 밀어올림 (수중 표현은 범위 밖)

### 14-3. 사이트 안에서의 입력 처리

- 키 입력은 포인터가 잠겼거나 캔버스에 포커스가 있을 때만 받는다. WASD·Space는 `preventDefault`로 페이지 스크롤 방지
- 리스너는 전부 월드 `dispose()`에서 해제 (월드 교체 시 다른 월드에 키 입력이 새지 않게)

### 14-4. 캐릭터 에셋

- 기존 `assets/models/knight-mesh.glb`는 스킨·애니메이션이 없는 정적 메시이고 37 MB라 쓰지 않는다
- P5는 캡슐로 시작해서 이동·카메라·물 상호작용을 먼저 완성한다
- 그 다음 idle/walk/run이 있는 리깅 캐릭터(CC0 라이선스)로 교체. `AnimationMixer`로 속도에 따라 블렌딩, 물이 깊을수록 재생 속도를 낮춘다

### 14-5. 프레임 순서

```
입력 → 캐릭터 이동 (직전 프레임 수면 높이 사용) → 카메라
  → 시뮬 소스 업로드 (구 위치·속도, 창 중심)
  → compute A → (B) → S × N서브스텝 → C → render
  → 플레이어 주변 수면 높이 비동기 읽기 요청
```

시뮬은 고정 dt 누적기로 돌린다(E9). 렌더 프레임과 시뮬 스텝 수가 분리돼야 프레임이 떨어져도 시뮬이 터지지 않는다.

## 15. 프레임 예산 (목표, 측정으로 검증)

| 항목 | 목표 |
|---|---|
| 베이크 파도 (compute A + B + C) | ≤ 2 ms |
| 로컬 시뮬 (compute S, 서브스텝 합계) | ≤ 1.5 ms |
| 렌더 (지형 + 수면 + 캐릭터) | ≤ 4 ms |
| 캐릭터·카메라 (CPU) | ≤ 0.5 ms |

엔진 대응: 플레이어 주변 렌더타깃 핑퐁 파동 시뮬은 UE(렌더 타깃 + 머티리얼 기반 interactive water, Niagara Fluids)와 Unity(커스텀 RenderTexture/Compute 리플) 양쪽에서 흔히 쓰는 기법이다. 이 Lab은 그걸 논문식 베이크 파도와 한 수면에서 합치는 것이 다른 점이다.
